2.0.42-dev 按用户补充的 200 视频示例更改保留规则。已完成 100 个后停止预读补充；实际选中视频变化才推进观看批次，看完第一批 5 个仍保留，再看完一批 5 个后释放最早那 5 个并补足空位。后台读取和重播不作为新的观看进度，不使用读取时间淘汰尚未观看的视频。当前视频即使向后回看也从释放集合排除。缓存仍仅在当前进程内保存。

例如先缓存 1–100：进入第 6 个时仍保留 1–100；进入第 11 个时释放 1–5、保留 6–100，再补 101–105。到第 16 个再释放 6–10 并补下一批。29 项相关回归通过，包含按此顺序连续补充至第 200 个、每批腾出 5 个空位、完整字幕保留、后台读取不推进观看以及前台请求与批次调度。

新增 TikTok Minis 净化，放在顶部导航分组，控制经核对的首页侧栏服务中的可用性、当前 Activity 可用性和打开请求。未知服务形态独立失败并报告，不拖累其他布局净化。

原预读只在字幕显示时启动，当前轨道地址缺失便提前返回；后续窗口最多 4 个视频且每个仅取开头 6 句，总翻译缓存为 256 句，不能视为后续视频完整翻译。2.0.40-dev 从实际选中视频的生命周期触发，按实际列表位置读取后 5 个视频的字幕文件；当前视频无字幕仍可预读后续字幕。当前句走优先通道，后续按视频交错翻译完整时间轴，成功译文按视频保存。保留 100 个已完成视频以及最多 6 个进行中视频的临时译文，按最近使用顺序整体淘汰；缓存只在本次宿主进程中存在。

无字幕轨、字幕仍未由宿主提供、仅有实时字幕或文件读取失败的内容无法凭空提前生成译文。诊断分别记录五视频窗口及可读轨道数、文件解析句数、下载失败类型、预读翻译成功和缓存视频数；注册成功不作为预翻译成功证据。

## 2.0.37 统一包体积修正

2.0.36 约 60 MB，拆包确认外层 DEX 约 43 MB，内嵌运行时压缩后约 13 MB。虽然已切换正式签名并关闭调试，两种统一包构建类型继承 Debug 后遗漏 R8 和资源裁剪，属于构建配置问题。2.0.37 对两层都启用代码优化和资源裁剪，保持代理接口与加载入口。

两套分别压缩的代码可能将不同类混淆为相同短名，因此内嵌运行时的加载器优先读取其自身依赖，Android／JDK／传统 Xposed API 委托框架。包校验仍检查现代与传统入口、私有 API、父类及适配资料一致性，功能未因体积目标被删除。最终正式 APK 为 9,053,954 字节，较 2.0.36 减少 85.6%；外层 DEX 约 2.64 MiB，内嵌运行时压缩后约 2.87 MiB。

## 未发行：初始化等待自旋的实际调用栈

用户点击性能采样后，通过 ADB 读取当前采样窗口，确认 AsyncTask #3/#4 均位于 PreloaderInAppInit.LJIILIIL，由两个后台初始化任务调用。进一步只读拉取安装 APK 并检查内嵌原始 DEX：该方法只有 getBaseContext、空值回跳、启动 long 标记读取、零比较回跳和 return，无休眠。两个条件不满足时持续空转。

## 未发行：LSPatch 拒绝 API 命名空间、作者字幕及设置入口

用户提供的 LSPatch 报告明确包含 VectorModuleManager 错误 `The Xposed API classes are compiled into io.github.meiyongai.toki.subtitle`，发生在模块回调之前。上一专用包只检查传统 API 桩未打包，遗漏现代 API 也被该加载器禁止的限制；这是构建兼容错误，与用户卸载重装无关。新脚本从依赖 AAR 重定位现代 facade 的字节码常量和包路径，同时生成重写引用的源码副本，普通构建仍使用原源码。最终校验读取 DEX class_defs，拒绝两种框架 API 原命名空间，检查私有接口、传统入口和适配资源。

LSPatch 以共享内存加载 DEX，不能假定 Class.getResourceAsStream 总能读取模块 Java 资源。读取规则、扩展档案和预置档案增加模块 APK ZIP 备用入口。启动增加 Application.attach 边界，成功加载后首个前台页面提示版本与长按首页入口；不依赖 ADB。

字幕诊断中有多次带正文的 HIDDEN 状态，无法仅凭日志确定所有作者字幕内部布局。新增保守可见性补偿：只有唯一匹配当前正文的原生字幕控件已显示时，允许 HIDDEN 自动字幕状态驱动样式与翻译；不可见或旧正文仍不显示。这个修复不能覆盖宿主根本不发帧、没有独立文字控件或烧录在视频画面中的字幕。

用户补充隐藏功能指“翻译更多东西”和“始终翻译”。本轮增加翻译反向门控的业务键关系恢复；不对任意 Boolean getter 放行，不把恢复这一门控当作所有原生设置行已显示的证据。长按字幕入口改为专用编辑器，预览固定在滚动参数区上方，主页入口仍保留完整设置。仅提供本地 Debug 与 LSPatch 测试包。

## 未发行：LSPatch 集成入口缺失

用户反馈 TikTok 47.4.16 集成模式完全无响应，长按首页也无法打开。代码核对发现之前只有 META-INF/xposed 下的现代 API 102 入口，Manifest 最低版本也为 102；传统 LSPatch 没有可加载的 assets/xposed_init。此前添加宿主配置和内嵌设置仅解决模块加载后的依赖，没有解决传统框架的入口兼容；不能将之前本地测试理解为 LSPatch 加载已验证。

新增 lspatch 独立构建：编译时使用传统 Xposed API 82（编译桩不进入 APK），运行时由 LSPatch 提供传统实现；该构建携带共享业务所需的现代接口 facade，以传统 Hook 调用转接。普通 Debug 仍由现代框架提供 API。兼容层将同一方法的多个 Toki 拦截器按优先级串联，支持替换参数、接收者、取消和替换拦截器，原始调用异常解包保留，不将失败重试成第二次调用。不支持的框架能力明确拒绝，deoptimize 返回不支持。

集成模式的模块副本位于修补后的 TikTok 内，需要用新专用 APK 重新修补原始 TikTok。配置、字幕适配与窗口资源仍可能受具体 LSPatch 分支和 Android 版本影响；本次只能验证构建、入口打包和兼容层逻辑，不能替代用户当前 47.4.16 的实机加载和字幕验收。不要求 ADB，不上传宿主 APK、诊断或用户内容。

## 2.0.16 自动适配机制

- 基础功能沿用现有 DEX 发现；字幕扩展单独按完整代码集合、结构配置摘要和格式版本缓存，宿主更新或配置变化后重新查找。
- 匹配类形状、方法指令与控制流、字段使用位置。较大的混淆类允许无关方法变化，但至少 8 个方法且不少于双方方法数的 60% 必须保持一致，并验证继承关系；实际使用的每个成员仍需独立证据，不能仅凭类相似就挂钩。
- 相同签名的抽象接口使用独立调用位置或具体服务实现的指纹补充证据。字段可由其他类中未变化的读写位置识别。多个候选、多个角色占用同一个类或证据冲突时拒绝匹配。
- 评论投票通过真实 `onBindItemView` 桥接调用定位绑定方法，并交叉验证标题到 `setText`、选项正文到 `setOptionLabel`、绑定与更新共用的选项排序方法和控件列表。标题渲染通过已核验视频字段的唯一写入入口定位；字幕帧入口必须读取已核验的文本与状态字段，并调用已核验的渲染器。
- 翻译开关规则在保留寄存器、控制流和实验配置链接证据的前提下容忍混淆调用名变化。47.0.3 与 47.4.3 的这组语义摘要相同，无需为新版另填入口名称。
- 字幕、字幕轨补偿、长文案与评论投票保留独立注册事务；匹配失败不再撤销基础翻译。扫描失败可记录扩展不可用，基础扫描结果仍能保存。
- 未知版本首次运行需要等待后台发现；保存并核对后在主线程自动安装已匹配的功能，切换视频刷新已有内容，无需连接电脑或再次重启。匹配不等于完整画面验收；新版字幕、清屏、长文案和评论投票仍需实机回归。
- 维护者可用 `scripts/GenerateExtensionProfile.java` 和本地授权参考 APK 重新生成结构配置；配置只包含摘要、类型及成员描述，宿主 APK 和反编译内容不得提交。

### 减少重复修复的验收流程

1. 宿主更新自动使旧代码缓存失效；后台扫描完成后自动应用已验证入口，之后复用本机验证结果。模块规则升级时逐项保留未变化的基础结果，只补查变化依赖。
2. 翻译开关、字幕轨补偿、字幕显示、原生标题翻译、标题布局补偿与评论投票分别注册。某一入口失配时记录具体契约，其他入口继续尝试安装。
3. 开发阶段先离线扫描实际宿主安装包，检查字幕、清屏帧入口、标题布局、投票绑定和翻译传输依赖，再构建一次候选 Debug。单元测试覆盖改名、局部变化、歧义拒绝、桥接与字段关系，以及规则变化后的缓存复用。
4. 真机验收分成“适配结果完整”“挂钩实际注册”“译文实际显示”三层。集中检查普通字幕、清屏字幕、长文案与评论投票；仅请求成功或挂钩成功不能判定画面修复。
5. GitHub 默认只测试并构建 Debug；手动工作流明确选中 Release 才额外构建。未来宿主完全更换翻译服务、字幕通道或 UI 框架时仍可能需要维护规则，自动匹配不代表保证所有未来版本兼容。

“100% 后长时间等待”曾由基础扫描进度未切换到字幕扩展阶段引起。现在扩展使用独立提示，不沿用基础扫描百分比；只有保存与回读核对成功才显示完成。同时收紧原生候选筛选和字段证据的指令检查范围。未改变宿主代码、适配规则和参考配置时复用缓存，不应反复扫描。

2026-10-19 在 47.4.3 真机确认：基础扫描后显示“正在适配字幕扩展”；扩展缓存已保存，随后启动直接复用。字幕、字幕轨补偿、标题布局补偿、评论投票已注册，诊断记录标题译文写入布局。原生标题资格入口仍有独立契约未匹配，使用标题布局补偿；这不代表所有视频、清屏场景和投票画面均已验收。进一步加入方法数量和继承结构预筛选，离线扫描耗时约 13.4 秒，仍为 46 个类、380 个未解析成员；未解析成员包含参考类中未使用的成员，不能将类匹配数视为所有功能通过。

后续在 46.9.3 验证自动补偿：首次基础与扩展发现约 75 秒；补偿规则升级后的扩展重新发现约 49 秒，其中原生候选为 62,403 个。以上是当前设备单次样本，不同代码集合及设备不能直接作速度比。扫描、保存核对、功能自动注册均在同一宿主进程完成；字幕显示、字幕服务补偿、原生标题资格、标题布局补偿和评论投票均已注册，原生文字翻译通道已就绪。私有选择器和缓存读入口失配时保留已核验服务路径。仍需按实际内容核对普通字幕、清屏与投票的最终画面，不能仅凭注册成功宣称所有内容均正常。

本轮完整 537 项测试通过；Debug 构建与 lint 通过，lint 为 0 错误、28 项警告。资源目录包含全部提示键，尚未新增翻译的语言使用英文提示。自动适配在手机本地运行，电脑只用于开发验证。大幅重写或证据不足的宿主入口仍会保留原行为并记录诊断，不以任意挂钩代替适配。
